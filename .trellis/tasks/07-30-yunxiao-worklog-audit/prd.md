# brainstorm: 云效团队工时填写检测

## Goal

在 BU 管理系统中增加“云效工时检查”，按天检查纳入统计的团队成员是否在云效
Projex 登记实际工时，识别未填写、填写不足、完整和豁免日期，供负责人每日跟进和
按周期复盘。云效是事实来源，本系统只读取、汇总和展示，不代替成员登记工时。

## What I Already Know

- 当前系统已有用户、项目、任务、本地工时记录和统计权限，但尚无云效账号映射。
- 云效提供个人访问令牌认证的 OpenAPI。
- `SearchWorkitems` 只能按单个项目或项目集搜索工作项，不支持一次跨多个项目。
- `ListEffortRecords` / `ListWorkitemTime` 只能按工作项查询实际工时明细，返回登记人、
  实际工时、起止日期、类别和描述。
- 因为没有“按组织、人员、日期直接获取全部工时”的公开接口，实现时需要：
  项目范围 -> 工作项列表 -> 各工作项工时记录 -> 按人员和日期汇总。
- 云效默认工作日为周一至周五、每天 8 小时，并允许组织配置特殊工作日、休息日；
  跨日期工时会按工作日分摊。
- 云效用户只能登记自己的工时，因此本功能不应提供代填入口。

## Assumptions (Temporary)

- 采用云效中心版接口；部署时允许切换为 Region 版服务地址。
- 团队未开通云效效能洞察高级版，因此不能依赖组织级工时异常报表。
- 云效个人访问令牌使用“项目协作：工作项只读、实际工时只读、项目成员只读”权限。
- 检测范围默认是本系统所有启用且完成云效账号映射的团队成员，`admin` 不参与统计。
- 默认每天应填 8 小时，周末和维护的节假日不要求填写。
- 当天在截止时间前显示“待填写”，截止后 0 小时为“未填写”，大于 0 且不足应填
  工时为“填写不足”，达到应填工时为“已完成”。
- 请假、调休、出差等特殊日期通过豁免记录处理，避免误报。
- MVP 只读云效，不自动修改或补写工时。

## Open Question

- 无阻塞性产品问题；实施前需要提供云效版本、服务地址、组织 ID、只读 Token 和首批项目 ID。

## Requirements (Evolving)

### 0. BU 方向计划与负责人驾驶舱

- BU 负责人可维护少量跨项目“大方向”，包括目标、负责人、计划周期、关联项目和里程碑。
- 方向进度默认从关联项目的需求状态和任务完成度自动汇总，禁止只靠人工填写一个百分比。
- 方向健康度综合计划时间、逾期需求、阻塞任务、里程碑和云效交付状态，输出正常、关注、风险。
- 驾驶舱支持按方向下钻到项目、需求、云效工作项和负责人。
- 展示每个人的当前工作项、在途任务、逾期事项、过去实际投入率和未来计划负荷率。
- “饱和度”用于资源安排，不作为个人绩效评分；实际投入和计划负荷必须分开呈现。
- 云效预计工时存在时作为计划负荷主要来源；未接入或缺少预计工时时回退到本地任务预计工时，
  并显示数据完整度。
- 默认未来负荷窗口为 10 个工作日，可切换 5/10/20 个工作日。
- 负荷建议分层：低于 60% 可调配、60%-100% 合理、100%-120% 饱和、超过 120% 超负荷；
  数据完整度不足时显示未知，不强行计算。

### 1. 集成配置

- 配置云效版本、服务地址、组织 ID、个人访问令牌和同步计划。
- Token 由部署环境变量或密钥管理提供，禁止明文写入数据库、日志和前端。
- 管理员可执行连接测试，结果只显示权限和连通性，不回显 Token。

### 2. 人员与项目范围

- 维护本系统用户与云效 `userId` 的一对一映射。
- 支持按姓名或邮箱辅助匹配，但必须人工确认，不能只按重名自动绑定。
- 维护需要扫描的云效项目/项目集及工作项类型。
- 可将实习、外包、离职、管理岗位或特定人员排除在统计范围外，并保留生效日期。

### 3. 数据同步

- 定时和手动同步配置范围内的项目、工作项及实际工时明细。
- 每次同步记录开始/结束时间、扫描项目数、工作项数、工时数、失败数和错误摘要。
- 外部工时记录按云效记录 ID 幂等写入，支持修改和删除后的对账。
- 同步失败时不得把“没有拉到数据”误判为“员工未填写”，页面显示“数据未知”。
- MVP 可每日全量扫描范围内工作项；数据量增大后使用增量同步并每周全量对账。
- 对云效限流、超时和 5xx 做指数退避；控制并发，避免短时间逐工作项打爆接口。

### 4. 工作日与判定

- 维护组织工作日历：常规工作周、法定节假日、调休工作日和每天标准工时。
- 支持人员日期豁免：请假、调休、入离职边界、无需填报等，并记录原因和操作人。
- 跨多日工时按有效工作日分摊；无法确认分摊口径的记录标记为“待核对”。
- 每个“人员 + 日期”只产生一个最终状态：
  - `PENDING`：未到截止时间；
  - `MISSING`：截止后实际工时为 0；
  - `INSUFFICIENT`：实际工时大于 0、低于应填工时；
  - `COMPLETE`：实际工时达到应填工时；
  - `EXEMPT`：非工作日或已豁免；
  - `UNMAPPED`：未绑定云效账号；
  - `UNKNOWN`：同步失败或数据不完整；
  - `REVIEW`：跨日分摊等口径无法可靠判断。
- 超过标准工时可展示“超额”，但仍计入完成，不作为负面异常。
- 每个工作日 18:30 执行预检查：未达标人员显示“待补填”，用于当日提醒，不进入最终缺失统计。
- 次一工作日上午 10:00 执行最终检查：固化上一工作日的缺失或不足状态，纳入异常统计。
- 10:00 后补填的工时在下一次同步后更新历史状态，同时保留首次判定和补填时间用于审计。
- 遇周末或节假日，“次一工作日”按工作日历顺延。

### 5. 页面

- 在“数据分析”下增加“工时填报检查”。
- 默认显示最近 7 个工作日，可切换日期、项目、人员和状态。
- 顶部展示应填人日、已完成、未填写、填写不足、未知和填报完成率。
- 主视图使用“人员 x 日期”矩阵，单元格显示当日小时数和状态颜色。
- 支持“只看异常”，点击单元格查看云效工作项、工时类别、描述和同步时间。
- 提供异常明细列表和 Excel/CSV 导出，便于负责人跟进。
- 页面显示最近成功同步时间、同步进行中和同步失败状态。

### 6. 权限

- 管理序列和授权负责人可查看团队数据、维护映射和豁免、手动同步、导出。
- 普通成员只查看自己的每日状态和明细。
- Token、组织 ID 和内部错误堆栈不得返回前端。
- 手动同步、映射变更、豁免和导出均记录审计日志。

## Recommended Architecture

```text
云效 Projex OpenAPI
  -> 定时同步器（项目 -> 工作项 -> 工时明细）
  -> 外部工时原始表（幂等）
  -> 工作日历 + 人员映射 + 豁免
  -> 每日合规快照
  -> 团队矩阵 / 异常列表 / 导出
```

## System Boundary and Source of Truth

当前 BU 管理系统和云效 Projex 都具备项目、人员、需求、任务和工时能力。不能把这些
对象全部做双向同步，否则会产生两个事实来源、循环更新和状态冲突。

### Recommended Responsibility Split

| 业务对象 | BU 管理系统职责 | 云效职责 | 权威来源 |
|---|---|---|---|
| 客户、联系人、业务线 | 客户和业务组织管理 | 不维护 | BU 管理系统 |
| 商机/原始需求 | 收集、澄清、可行性、报价、客户确认和经营决策 | 研发前不创建 | BU 管理系统 |
| 项目治理 | 主/子项目、客户归属、经营负责人、整体交付视图 | 研发空间、项目成员和迭代 | 分层负责，不双向覆盖 |
| 研发需求 | 保存业务需求及交接状态，记录云效工作项 ID | 开发阶段的需求拆分和状态流转 | 进入开发后以云效为准 |
| 开发任务 | 只显示云效任务摘要或高层交付包，不再维护明细开发任务 | 任务、子任务、缺陷、迭代、负责人 | 云效 |
| 实际工时 | 只读同步、检查缺失、汇总展示，不允许编辑 | 成员登记、修改和删除工时 | 云效 |
| 预计工时/报价 | 售前评估、成本报价继续保留 | 研发拆解后的执行预计工时 | 各自保留，字段名称明确区分 |
| 代码、合并请求、流水线 | 仅展示链接或摘要 | Codeup、Flow 与工作项联动 | 云效 |
| 人员岗位、系统权限 | BU 岗位和管理权限 | 云效账号、项目角色 | 各自负责，通过 userId 映射 |

### Integration Point

```text
BU 原始需求
  -> 评估 / 报价 / 方案 / 客户确认
  -> “进入开发”时异步创建或绑定云效研发需求
  -> 云效拆任务 / 排迭代 / 记缺陷 / 填工时 / 关联代码
  -> BU 系统只读回传研发状态、实际工时、异常和交付结果
```

### Automatic Handoff to Yunxiao

- 触发条件：需求完成客户确认或内部确认，状态首次进入“开发中”。
- 当前系统项目必须先配置云效项目 ID、工作项类型 ID 和必要的自定义字段映射。
- 已存在有效绑定时不重复创建；未绑定时创建云效研发需求。
- 支持在自动创建前手动绑定一个已有云效工作项，适配历史需求和云效先建场景。
- 创建内容包括本系统需求编号、标题、需求描述、优先级、期望日期、负责人和回链地址。
- 云效工作项增加稳定的“BU需求ID”自定义字段或等价唯一标识，用于超时重试前查重。
- 创建成功后保存云效工作项 ID、编号、链接、项目、创建时间和同步状态。
- 交接成功后，云效负责研发状态和执行字段；当前系统不再覆盖云效任务拆解和实际工时。

### Handoff Reliability

```text
需求状态事务
  -> 写入 yunxiao_handoff_event（PENDING）
  -> 后台任务调用云效 CreateWorkitem
  -> 成功：创建关联，事件 SUCCESS
  -> 失败：指数退避重试，事件 RETRYING/FAILED
  -> 人工：重新同步或绑定已有工作项
```

- 云效接口不可用时不回滚需求“开发中”状态，避免外部故障阻断内部业务流程。
- 页面必须明显展示“待同步、同步中、已关联、同步失败”，负责人可处理失败任务。
- 使用本地唯一约束 `requirement_id` 和云效稳定业务标识双重防重。
- 对“请求已成功但响应超时”的不确定结果，重试前先按稳定业务标识搜索云效。
- 自动重试达到上限后停止，并通知负责人；禁止无限重试。
- 所有创建、重试、人工绑定、解绑操作记录审计日志。
- 解绑只解除系统关联，不自动删除云效工作项。

### Conflict Handling Rules

- 同一字段必须指定唯一权威来源，不进行“最后写入者获胜”的双向覆盖。
- 进入开发前，需求状态由 BU 系统控制；进入开发后，研发执行状态由云效回传。
- BU 系统现有 `work_log` 仅保留给不使用云效的项目；云效覆盖项目禁用本地工时编辑。
- BU 系统现有开发任务逐步降级为“交付工作包/摘要”，不要求研发人员两边维护。
- 同步使用云效工作项 ID、工时记录 ID 和 userId 做稳定映射，姓名只用于显示和人工匹配。
- 云效删除、归档或权限变化不直接删除 BU 业务需求，只标记外部关联状态。
- 同步方向默认为“BU 创建研发交接项 -> 云效；云效状态和工时 -> BU”，不做全量双向同步。

### Suggested Data Model

- `bu_direction`：BU 大方向、目标、负责人、周期、状态和健康度覆盖说明。
- `bu_direction_project`：方向与一个或多个本系统项目的关联。
- `bu_direction_milestone`：里程碑、负责人、截止日、完成标准和状态。
- `yunxiao_integration_config`：版本、服务地址、组织 ID、启停和同步计划，不存 Token。
- `yunxiao_user_mapping`：本系统用户、云效 userId、显示名、统计启停和生效区间。
- `yunxiao_project_scope`：云效项目/项目集、工作项类型和是否启用。
- `yunxiao_workitem_cache`：工作项 ID、项目、类型、标题、状态和最后修改时间。
- `yunxiao_effort_record`：外部记录 ID、工作项、人员、起止日期、工时、类别和描述。
- `workday_calendar`：日期、是否工作日、标准工时和备注。
- `worklog_exemption`：人员、日期、豁免类型、原因、操作人。
- `worklog_daily_snapshot`：人员日期、应填/实际工时、状态、同步批次和计算时间。
- `yunxiao_sync_job`：同步批次、阶段、统计、状态和错误摘要。
- `yunxiao_project_mapping`：本系统项目与云效项目、工作项类型和字段映射。
- `yunxiao_workitem_link`：需求与云效工作项的一对一关联、编号、链接和同步状态。
- `yunxiao_handoff_event`：交接事件、重试次数、下次执行时间和错误摘要。

## Feasible Approaches

### A. OpenAPI 同步到本地（Recommended）

- 通过云效只读 Token 定时同步原始工时，本地计算每日状态。
- 优点：可追溯、可做历史趋势、提醒和导出；云效短时不可用时仍能查看上次结果。
- 缺点：按工作项拉工时，请求量较大，需要缓存、重试和对账。

### B. 直接使用云效效能洞察（Not Available）

- 在云效创建工时效率/工作负荷报表，本系统只放入口链接。
- 优点：成本最低，工作日和工时分摊由云效负责。
- 结论：团队未开通高级版，不作为当前方案。

### C. 定期人工导出后导入

- 从云效导出实际工时文件，再上传本系统计算缺失。
- 优点：不需要 Token 或复杂 API 遍历，适合快速试运行。
- 缺点：不自动、时效差、容易漏传，不适合作为最终方案。

## Delivery Plan

### Phase 0: API PoC（1-2 天）

- 用只读 Token 验证版本、服务地址、组织、项目和成员接口。
- 选 1 个项目、3 个成员、最近 5 个工作日验证工作项枚举和工时明细。
- 核对跨日工时、修改/删除工时、历史工作项补填是否能被正确发现。
- 输出 API 请求量和全量同步预计耗时；PoC 不通过则降级为导入方案。

### Phase 1: 数据底座（3-5 天）

- 完成配置、人员映射、项目范围、原始工时、同步任务和审计表。
- 实现只读客户端、限流重试、幂等同步、手动同步和同步状态接口。
- 接入工作日历及日状态计算，完成单元和集成测试。

### Phase 2: 检查页面（3-4 天）

- 完成汇总指标、人员日期矩阵、异常筛选、详情和导出。
- 完成人员映射、项目范围和豁免管理。
- 增加角色权限、空数据、同步失败、未映射和移动端状态。

### Phase 3: 上线观察（2 天）

- 与云效工时统计人工对账至少 5 个工作日。
- 对账通过后开启每日定时同步；首周只展示，不自动催办。
- 记录误报原因并调整工作日、豁免、跨日分摊和截止时间规则。

### Phase 4: 通知闭环（Optional）

- 企业微信/钉钉按负责人汇总提醒，避免公开点名。
- 支持 D 日提醒、D+1 复核和连续缺失升级。
- 通知必须可配置、可停用、可追踪且避免重复发送。

## Confirmed Decisions

- 当前系统负责需求前期：客户、业务线、需求收集、澄清、评估、报价、方案、确认和经营决策。
- 云效负责研发执行：研发工作项、迭代、任务、缺陷、实际工时、代码和流水线。
- 当前系统负责最终汇总：只读接入云效研发状态、工时、异常、交付结果并进行跨项目分析。
- 云效是研发执行数据的唯一事实来源，当前系统不提供云效项目的任务和实际工时代填。
- 团队没有开通效能洞察高级版，MVP 选择 OpenAPI 本地同步方案。
- 本系统现有任务和工时能力只保留给未接入云效的项目；接入云效的项目切换为只读摘要。
- 需求完成客户/内部确认并进入“开发中”时，自动创建或绑定云效研发工作项。
- 云效交接采用事务事件和后台异步重试，不因云效短时故障回滚本系统需求状态。
- 工时检查采用双阶段口径：当日 18:30 预警，次一工作日上午 10:00 最终判定。
- BU 负责人驾驶舱同时覆盖方向计划进度、项目风险、人员工作明细和资源饱和度。
- 实际投入率与未来计划负荷率分开展示，饱和度不作为绩效分数。

## Acceptance Criteria (Evolving)

- [ ] 已映射且纳入统计的成员可按工作日看到应填和实际工时。
- [ ] 0 小时、填写不足、完整、豁免、未映射和同步未知状态判定准确。
- [ ] 同步失败不会产生“未填写”误报。
- [ ] 工时详情能追溯到云效工作项和外部记录 ID。
- [ ] 修改后的云效工时在下一次同步后更新，不产生重复记录。
- [ ] 团队负责人可筛选和导出异常，普通成员只能查看本人。
- [ ] 与云效人工统计连续 5 个工作日对账一致。
- [ ] Token 不出现在数据库、接口响应、日志和前端资源中。

## Definition of Done

- 后端单元测试、云效客户端契约测试和同步集成测试通过。
- 前端类型检查、生产构建和关键 Playwright 流程通过。
- 完成真实云效项目的小范围对账和失败演练。
- 部署文档包含 Token 配置、轮换、同步重试、停用和回滚方法。
- 数据库迁移可回滚，功能支持配置开关。

## Out of Scope

- MVP 不替员工向云效代填或修改工时。
- MVP 不接入考勤、薪资或绩效评价。
- MVP 不自动判断请假，先由负责人维护豁免。
- MVP 不公开展示个人排名。
- MVP 不在云效同步失败时发送缺失提醒。

## Technical Notes

- 云效实际工时只读接口：
  `GET /oapi/v1/projex/organizations/{organizationId}/workitems/{id}/effortRecords`
- 云效工作项搜索接口一次只支持一个项目或项目集，最大分页大小为 200。
- 认证请求头为 `x-yunxiao-token`；只申请工作项、实际工时和项目成员只读权限。
- 云效工时工作日规则会影响跨日记录分摊；PoC 必须验证实际返回口径。
- 当前项目相关实现：
  - `backend/.../entity/User.java`
  - `backend/.../entity/WorkLog.java`
  - `backend/.../service/WorkLogService.java`
  - `frontend/src/views/TasksView.vue`
