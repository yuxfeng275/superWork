# 云效需求、任务、缺陷分开展示设计

## 目标

在现有需求管理和任务管理中统一展示本地记录与云效只读记录，并新增独立缺陷管理页面展示云效缺陷。需求、任务、缺陷始终分开，云效仍是云效记录的唯一权威数据源。

## 已确认决策

- 云效记录只读，不复制到本地 `requirement`、`task` 或新增缺陷业务表。
- 采用同一列表统一展示方案，以来源标识区分本地和云效。
- 缺陷管理首期仅展示云效 `Bug`，不支持本地新建。
- 已绑定云效的本地需求合并为一行；未绑定云效需求才独立显示。
- 显示云效原始状态，并归一化为 `PENDING`、`IN_PROGRESS`、`COMPLETED`、`OTHER` 用于统一筛选统计。
- 首次同步全部历史数据，后续增量同步。
- 多个本地项目共享一个云效空间时，工作项全局只显示一次，并关联全部映射项目；绑定需求以本地需求项目为准。

## 架构

云效同步服务把 `Req`、`Task`、`Bug` 写入 `yunxiao_workitem_cache`。统一查询层在服务端把本地业务数据与云效缓存合并，完成项目权限过滤、需求绑定去重、状态归一化、排序、分页和统计。前端只消费类型化的统一查询响应，所有本地写接口保持不变。

统一查询接口：

- `GET /api/requirements/overview`
- `GET /api/tasks/overview`
- `GET /api/defects/overview`
- `GET /api/yunxiao/workitems/{id}`

统一记录包含 `recordKey`、`source`、`readOnly`、本地 ID、云效工作项 ID/编号、项目集合、负责人、原始状态、归一化状态、工时和源时间。云效原始 JSON 不通过 API 直接返回。

## 缓存与映射

`yunxiao_workitem_cache` 增加 `yunxiao_project_id`、`normalized_status`、`source_created_at`、`source_updated_at`、`active`。共享项目归属通过 `yunxiao_project_mapping.yunxiao_project_id` 关联，不使用缓存中的单一 `project_id` 判断统一列表归属；旧字段保留兼容驾驶舱。

`yunxiao_project_mapping` 增加 `full_synced_at`。同一云效空间只执行一次同步，并把结果写回其全部映射。首次全量同步结束后记录时间；后续基于最后成功时间增量拉取。全量校准未再次出现的缓存记录为无效，列表不展示无效记录。

## 查询与去重

- 需求：本地需求始终保留。若 `yunxiao_workitem_link` 指向缓存记录，则将云效编号、状态和同步时间附加到本地记录并排除对应云效独立行。
- 任务：本地 `task` 与云效 `Task` 按来源形成独立记录，不推断二者相同。
- 缺陷：仅查询云效 `Bug`。
- 共享云效空间记录返回全部可见的本地项目；全局只计数一次。
- 项目级角色只看到其参与项目或映射云效空间下的记录；管理角色沿用现有全量权限。

## 页面交互

工作台导航新增“缺陷管理”。三个页面统一使用来源筛选与来源标签：本地为蓝色，云效为黄色。云效记录不展示编辑、删除或状态变更操作；点击打开只读详情。已绑定需求显示“本地”和“已关联云效编号”两个标识。

三个页面以统计分析为主、明细下钻为辅：指标带之后展示状态、项目、负责人、来源等当前快照分布，需求增加优先级分析，任务增加预估/实际工时执行率；点击分布项联动明细筛选。缺陷页保留关键词、项目、负责人、归一化状态筛选和服务端分页。页面显示最近同步时间。没有每日状态快照前不展示历史趋势，避免使用当前缓存伪造趋势。

## 同步与错误处理

全量同步异步执行，避免全历史同步导致 HTTP 超时；已有增量同步入口保持兼容。首次全量只同步工作项基础投影：已有缓存工时保持不变，新发现的历史项工时为空；后续增量对发生变化的工作项继续同步预估与实际工时。同一云效空间只执行一次扫描，同一服务实例内的同步调用串行执行。

云效描述按类型化字段返回并在前端净化；认证令牌、原始 JSON 和内部错误堆栈不出现在响应中。未知状态进入 `OTHER`，但原始状态照常显示。

## 验收

- 三类云效工作项分别出现在需求、任务、缺陷页面。
- 已绑定需求无重复，未绑定需求显示为云效只读行。
- 本地记录原有创建、详情、编辑和状态操作不回归。
- 项目、负责人、来源、状态和关键词筛选以及分页统计准确。
- 共享空间全局不重复，项目过滤和数据权限正确。
- 首次全历史同步与后续增量同步均可观测，失败不会清空已有数据。
- 后端测试、前端构建和 Playwright 通过后部署到 `241`，触发全量同步并验证线上页面和分类计数。
