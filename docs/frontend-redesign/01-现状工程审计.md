## 2. 主要结构问题

### 2.1 页面单体过大

最大文件为 `KeyMattersView.vue`，约 7,765 行；需求、任务、统计、营收和详情页面也均超过 1,900 行。

页面同时承担：

- API 调用
- 表单状态
- 权限判断
- 列表渲染
- 弹窗和抽屉
- 业务计算
- 响应式样式
- 错误和加载处理

迁移时不能逐文件翻译，应按业务能力拆成 feature、query、form、table、drawer 和 permission boundary。

### 2.2 API 层集中且类型不完整

所有领域 API 基本集中在 `frontend/src/utils/api.ts`，部分返回值和表单数据依赖 `any`。新前端应建立 domain service 和 typed adapter，页面不得直接拼接请求结构。

### 2.3 状态管理缺少统一分层

当前 Pinia 主要用于认证；多数页面状态保存在页面内部，服务端状态、缓存、请求竞态和刷新策略未形成统一模式。新前端采用 React Query 管理服务端状态，局部表单状态留在 feature 内，全局只保存认证、权限和 UI 壳状态。

### 2.4 视觉规范存在冲突

当前仓库同时存在蓝色 UI 规范、紫色 Master 设计系统、页面硬编码颜色和 Element Plus 全局覆盖。迁移必须先确定单一 token 源，禁止逐页自由发挥。

### 2.5 包体和样式覆盖偏重

当前全量引入 Element Plus 和所有图标，构建主入口压缩后约 1.08 MB；工程中约有 133 处 `:deep` 和 81 处 `!important`。新工程要求按需加载、路由分包和 token 化样式。

## 3. 已有质量资产

- 已有路由和权限回归。
- 已有需求弹窗、云效工作项、营收、邮件、大事儿和响应式用例。
- `frontend-prototype/` 可作为历史交互参考，但不能当作当前生产行为的唯一事实来源。
- `.trellis/spec/frontend/` 和 `docs/superpowers/specs/2026-04-05-ui-ue-spec.md` 是迁移输入，不是可忽略的旧文档。

- `npm run build` 已通过。
