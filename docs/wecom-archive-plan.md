# 企微会话存档：立项设计（人读版）

> 更新时间：2026-11-07 · 相关：[ingest-oss-survey.md](ingest-oss-survey.md)、[fact-intake.md](fact-intake.md)、[fact-sop.md](fact-sop.md)、[wecom-integration-design.md](wecom-integration-design.md)
>
> 一句话结论：**内部群的消息今天就能进事实层（转发脚本 + `/wecom-hook`）；个人微信、外部联系人单聊要进系统，
> 必须先走「会话内容存档」授权，这是法务/合规决策，不是技术选型。**

---

## ① 为什么只做内部群

企微的消息分三类，采集权限完全不同：

| 消息类型 | 能不能采 | 依据 |
| --- | --- | --- |
| 公司内部群（自建群，成员都是本公司的人） | ✅ 可以，走群机器人/转发脚本 | 消息在自有应用可读范围内，成员知情 |
| **员工个人微信** | ❌ 不碰 | 属员工私人通信，不在企微开放能力内；任何绕过手段都是违规采集 |
| **外部联系人单聊（客户/供应商）** | ⚠️ 只能走「会话内容存档」 | 企微把这部分内容划入 msgaudit 范围，需企业管理员开通授权 |

所以本项目的边界画得很清楚：

- **不碰员工个人微信**；
- **不采外部联系人单聊**（除非存档授权开通，见下）；
- **不做屏幕/键盘/剪贴板采集**。

这不是"暂时不做"，而是默认不做。原因很直接：外部联系人单聊里有客户的报价、合同、私人信息，
一旦无授权采集，出问题的是公司而不是某个工程师。判断权在人（企业管理员 + 法务），
技术侧只负责"授权到位后能接上"。

`POST /internal/project-context/{projectId}/wecom-hook` 就是这条边界的技术落点：
`external == true` 直接 400，返回「外部联系人单聊不走本端点：需企业管理员开通会话内容存档（msgaudit）授权」，一行都不落库。

---

## ② 管理员要做什么（开通存档的四个动作）

会话内容存档（对外常称 msgaudit）不是装个 SDK 就能用，前提动作都在管理员侧，缺一不可：

1. **开通存档服务** —— 在企微管理后台购买「会话内容存档」席位（按人数/席位数收费，是付费项，需预算审批）。
   开通后才有拉取接口的调用资格。
2. **生成 RSA 公私钥，私钥由企业自持** —— 存档接口下发的消息体是加密的，解密私钥只存在企业自己的服务器上。
   腾讯不持有私钥，意味着**丢了私钥 = 历史存档永久读不出来**，运维要按密钥资产对待。
3. **给自建应用勾选「读取会话内容」权限** —— 存档能力挂在自建应用上，勾选权限 + 配置可信 IP 后才可调用。
4. **Secret 交运维做密钥托管** —— 应用的 Secret、私钥、解密口令一律走运维的密钥托管，**不入仓库、不进日志、
   不写进任何文档/工单/聊天记录**。代码里只读环境变量或配置中心。

第 2、3 步的产出（私钥、Secret）就是"授权到位"的物证；这三样没齐，技术侧不排期。

## ③ 技术形态

官方只提供 SDK，没有 HTTP 直连的省事做法：

- **C 版 SDK**：跑在 Docker 里，作为独立采集器进程，与主服务解耦；
- **Java 版 SDK**：内嵌进 Spring Boot（native 依赖，需要与 JDK/OS 架构对齐，升级时略麻烦）。

推荐**先 C 版跑 Docker**：隔离性好，升级 SDK 不影响主服务，故障只影响采集器。

拉取 → 落库的链路（每一步都能单独验收）：

```
企微服务端
  → [SDK] 拉加密消息（chatdata，按 seq 游标分批）
  → 本地解密（企业私钥，进程内完成，明文不外发）
  → 过滤：只留本公司成员 / 白名单群 / 命中敏感词复核
  → 归一成 CHAT_EXPORT 事实（source_ref = wecom:{sha256}，与内部群端点同一套键）
  → project_fact 落库（appendManual）
  → 夜间 agent 读事实 → 候选 → 制品 → 晨报
```

**关键设计点：写入路径与 `WeComInboundController` 完全一致。**
同一个 `SOURCE_CHAT_EXPORT`、同一个 `wecom:` 前缀幂等键、同一个 `appendManual(projectId, …, actorId, occurredAt, title, body, visibility)`。
带来的好处是：**没有存档授权时，「转发脚本 + 本端点」就能跑通全链路**——
事实格式、幂等、可见性、夜间闭环全部预演过一遍；等授权到位，只是把"转发脚本"换成"SDK 采集器"，
下游一行不用改。这也是为什么先做内部群端点，而不是等授权。

## ④ 增量与回填

- **增量**：按 `seq` 游标断点续传。游标持久化（每个会话一条），进程重启从上次 seq 继续；
  拉取失败不推进游标，天然支持重试，不会漏也不会重复（重复由幂等键兜住）。
- **回填**：首次接入可以回填历史，但**限 90 天、且有总量上限**（防一次性把库和夜间任务压垮）。
  回填与增量共用同一条写入路径，只是游标起点不同。
- 游标与回填批次都留审计记录：谁在什么时候触发了多久的回填。

---

## ⑤ 保留期

事实层的保留期按来源区分（`FactRetentionScheduler` 负责，见保留期任务）：

- `CHAT_EXPORT` 的 **body 默认 180 天清理** —— 聊天原文只作近期资料，不长期留存；
- **digest 与 source_ref 永久保留** —— 结论还在，指针还在，能证明"这条事实来自哪条消息"，但原文不可再读。

这条规则对内部群端点和存档采集器一视同仁：不管消息从哪条通道进来，原文都不长留。
敏感词/密钥类内容在落库前就应脱敏（见脱敏与保留期任务），保留期是第二道闸，不是第一道。

---

## ⑥ 合规要求（写进立项材料的硬条件）

1. **采集范围对本人可见** —— 员工能查到"自己的哪些消息被采了、进了哪个项目"，不做暗采；
2. **默认 `OWNER` 可见性** —— 存档进来的内容默认只给项目负责人看，不默认全公司可见，避免顺手扩散；
3. **可一键暂停** —— 管理员能立即停掉采集器（游标保留，恢复后从断点续），不需要改代码发布；
4. **审计留痕** —— 开通/暂停/回填/读数都要有记录：谁、何时、为什么；
5. **不用于绩效** —— 存档数据只服务项目事实层与交付判断，**明确不进入任何绩效/考勤/工时核算口径**。
   这一条要写进员工知情的说明里，否则合规上站不住。

## ⑦ 没有授权时的 SOP 兜底（今天就能跑）

存档授权是"未来态"，业务不能等。无授权期间的兜底是**人转关键结论**：

> 客户在群里/电话里给出的关键结论，**30 秒内**转到内部项目群，或直接发项目邮箱 `inbox+<code>@`（按项目别名路由）。

细则见 [fact-sop.md](fact-sop.md)。配套工具：

- 内部群转发 → `POST /internal/project-context/{id}/wecom-hook`（本设计交付的端点，转发脚本/群机器人直接调）；
- 投递箱 / `bin/huji-put chat` / 菜单栏投递 —— 见 [fact-intake.md](fact-intake.md)。

兜底的判断标准还是那一句：**"如果我明天休假，同事看这条能不能接着干？"** 能，就转。

## ⑧ 为什么不用那三个开源封装

本轮调研（[ingest-oss-survey.md](ingest-oss-survey.md)）评估了三个社区对企微存档的封装库，结论是不采用：

| 候选 | 结论 |
| --- | --- |
| 候选一 | **无许可证** —— 没有 LICENSE 文件等于默认保留所有权利，商用直接踩法律风险 |
| 候选二 | **无许可证** —— 同上，且 README 明确只说"学习交流用" |
| 候选三 | MIT，**但零维护** —— 最后一次提交停在 2022-09，官方 SDK 已换过接口，接上去等于自己维护一个 fork |

自研的成本其实很低（官方 SDK + 解密 + 一个游标 + 一条写入路径），
而这三个封装的成本是"看起来省了两天，实际背上了许可证风险或维护债"。
取舍原则：**依赖要么有明确许可证且有维护，要么干脆自己写。** 具体库名与链接见调研文档。

## ⑨ 交付边界（本设计要做/不做）

**做**：内部群入站端点（已交付）、存档采集器立项骨架（本文）、保留期与脱敏口径、合规清单、无授权 SOP。

**不做**：不碰员工个人微信；不采外部联系人单聊；不做屏幕/键盘/剪贴板采集；
不在未取得管理员授权与法务确认前采购存档席位。
