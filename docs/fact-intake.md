# 项目事实投递：一页说明（给团队）

> 更新时间：2026-11-07 · 相关：[project-agent-loop-plan.md](project-agent-loop-plan.md)、[ai-capabilities.md](ai-capabilities.md)

夜里跑的 agent 只认一张表：`project_fact`（项目事实层）。它读这里的事实，再决定今晚干什么、
明天早上推什么晨报。**这张表里没有的东西，对 agent 就等于没发生过。**
本页讲清四件事：为什么投、四个入口怎么用、投什么不投什么、没投的后果。

---

## ① 为什么要投：不投，夜里就是空转

夜间闭环（M0+M1）的链路是：

```
project_fact（事实）→ 候选（有证据才派活）→ agent 干活 → 制品 DRAFT → 人工评审 → APPROVED 后回流事实
```

- **无证据不派活**：候选必须挂 `source_ref` 才进夜间任务，事实层空 → 候选空 → 夜里啥也没干。
- 真干了也容易跑偏：只有周报和邮件这类自动汇入的信息时，产出往往是通用套话。

**例子（皇家项目）**：本周夜里出过 3 张 DRAFT 制品 —— 一张「标品升级差异处理方案」、
一张「京东积分多发复盘」、一张「排期调整建议」。三张的共同问题都是：
人工手里的关键材料（客户群里确认过的口径、线下对账的 Excel、录音里的口头结论）没进事实层，
所以 agent 只能按已有的碎片猜，结论大而全、落不到具体版本和具体人。
现在这 3 张都卡在 `IN_REVIEW`，评审要花时间，等于把投递的活儿挪到了评审环节——
**投递花 1 分钟，评审省 30 分钟。**

一句话：投递不是填表，是给夜里那台机器装眼睛。

## ② 四个入口怎么用

四个入口写的是同一张表，选顺手的即可，不用重复投（同一文件/同一段聊天重传不会新增事实）。

### 2.1 项目详情 →「投递箱」（最常用）

合拍 → 项目管理 → 点开某个项目 → 抽屉里「投递箱」三个页签：

| 页签 | 干什么 |
| --- | --- |
| 文件 | 拖文件进去（可多选），填一句补充说明，选可见性，投完提示「已入事实，今晚会用到」 |
| 说明 | 写标题 + 正文，适合口头决议、客户原话、结论这类没有文件的东西 |
| 聊天 | 粘贴企微/微信导出文本，自动按行拆成「[时间] 姓名: 内容」；拆不出来的整段当一条，不丢内容 |

下方列表能看到最近投过的文件 / 说明 / 聊天 / 制品，以及谁在什么时候投的。

### 2.2 菜单栏 `合拍·投递`（macOS，自动投）

适合「文件本来就落在某个目录里」的场景（桌面上的对账单、录音转写、客户发来的附件）。
配置一次监听目录，之后往目录里丢文件就自动投，不用再点任何东西。

首次配置见 [macapp/HepaiDelivery/README.md](../macapp/HepaiDelivery/README.md)：

1. 拖 `合拍投递.app` 到 `/Applications`，第一次**右键 →「打开」**（绕过 Gatekeeper 的「无法验证开发者」）。
2. 菜单栏出现「合拍·投递」→「配置窗口…」：服务器地址、账号、密码（密码进钥匙串，不写盘）、
   监听目录 + `projectId` + 可见性。
3. 目录里丢个文件，几秒后弹通知；菜单里「今日已投」+1。

### 2.3 命令行 `bin/huji-put`（脚本/批量）

只依赖 `curl` 和 `jq`，适合 SSH 上去批量投、或者写进自己的小脚本。

```bash
# 密码走环境变量，不落盘、不进进程参数
export HUJI_PASSWORD='你的合拍密码'

# 投文件（可多个）
bin/huji-put --base-url http://127.0.0.1:18081 --user zhangsan --project 1 \
  file ~/Desktop/对账单.xlsx ~/Desktop/验收单.pdf

# 投一条说明
bin/huji-put --base-url http://127.0.0.1:18081 --user zhangsan --project 1 \
  note "皇家 PMS 进度" "标品升级差异 4800 个，进度 15%，等张野出分类清单"

# 投聊天导出（按行解析「[时间] 姓名: 内容」，解析不出就整段一条）
bin/huji-put --base-url http://127.0.0.1:18081 --user zhangsan --project 1 \
  chat ~/Downloads/群聊导出.txt
```

`bin/huji-put --help` 有完整参数；`--visibility` 默认 `PROJECT`。
文件投递的 `note` 自动写「来自 huji-put / 主机名」，方便回溯是谁的机器投的。

### 2.4 群机器人 / 脚本 → `/internal/project-context/{id}/chat`

没有登录态也能投（群机器人、值班脚本、CI）。走内部端点，必须带 `X-Sidecar-Token`：

```bash
curl -sS -X POST "https://<合拍地址>/internal/project-context/1/chat" \
  -H "Content-Type: application/json" \
  -H "X-Sidecar-Token: $PROJECT_CONTEXT_TOKEN" \
  -d '{"messages":[{"time":"2026-11-06 14:22","sender":"客户-王工","text":"周五前要一版排期"}],"visibility":"PROJECT"}'
```

- 该端点的 `actor_id` 记 `null`（没有用户身份），正文里写清是谁说的。
- `PROJECT_CONTEXT_TOKEN` 由运维配置，别写进仓库、别硬编码进脚本。
- 同一段聊天重传不会新增（`source_ref` 用正文哈希去重）。

## ③ 投什么、不投什么

### 该投（有信息量的原始材料）

| 类型 | 长什么样 | 入口 |
| --- | --- | --- |
| 进度 | 「X 模块到 60%，Y 卡在接口权限」 | 说明 / 聊天 |
| 卡点 | 「等第三方开权限」「等客户确认口径」 | 说明 |
| 决议 | 「例会定了走方案 B，不再评估 A」 | 说明 / 聊天 |
| 客户反馈 | 客户原话、验收意见、拒收理由 | 说明 / 聊天 / 文件（截图） |
| 缺陷 | 线上问题单、异常日志、复现截图 | 文件 |
| 报价变更 | 报价单、变更单、折扣审批 | 文件 |
| 交付物 | 方案、原型、测试报告、验收单 | 文件 |
| 线下材料 | 对账 Excel、录音转写、会议白板照 | 文件 |

判断标准一句话：**「如果我明天休假，同事看这条能不能接着干？」** 能，就投。

### 不该投

- 闲聊、表情包、与项目无关的私事；
- 密码、密钥、身份证号、银行卡号（事实层会长期留存，不脱敏就会一直留在那里）；
- 别人的私人评价（可见性选错会直接造成人际关系问题，见下）。

### 可见性怎么选

| 值 | 谁能看 | 什么时候用 |
| --- | --- | --- |
| `PROJECT`（默认） | 项目成员（含客户侧参与人） | 绝大多数情况：进度、决议、交付物、客户反馈 |
| `PRIVATE_COMPANY` | 只有本公司的人 | 内部成本、毛利、报价底价、对客户的内部评价、还没对外说的排期 |
| `OWNER` | 只有项目负责人 | 极少数敏感内容；命令行/菜单栏支持，投递箱界面上只提供前两个 |

拿不准的时候：**客户看得到会不会尴尬？会 → `PRIVATE_COMPANY`。**
注意可见性影响夜间 agent 的取数范围：投成 `OWNER` 的事实，别的成员和部分 agent 场景读不到，
信息价值会被打折，别习惯性往最严选。

## ④ 没投进来的后果，和现在的覆盖

### 已经自动汇入的（不用手工投）

| 来源 | 说明 |
| --- | --- |
| 会议纪要 | 上传录音 → 转写 → LLM 纪要（决议/风险/待办），自动落事实 |
| 邮件 | 邮件摘要与单封解读，按项目/参与人归属后落事实 |
| 云效 | 工作项（需求/任务/缺陷）状态变化 |
| 大事儿 | 六态关键事项 + 周更表 |
| 周报 / KPI | 已发布周报与 KPI 计算结果 |

### 只能靠这四个入口的（自动汇不进来）

- **本机文件**：桌面/下载里的对账单、验收单、客户附件、录音原始文件；
- **聊天记录**：企微/微信里的口头决议、客户原话；
- **口头结论**：会上说的、电话里定的，谁也没写进任何系统；
- **线下反馈**：客户在现场说的、验收会上提的。

### 没投会怎样

1. 当夜候选为空 → agent 空转，第二天晨报只有「暂无建议」；
2. 事实碎片化 → 出了制品也是套话，评审退回，等于返工；
3. 周报缺素材 → 还得人工回忆补写；
4. 时间一长，事实层变成「只有邮件和会议」的半个项目，nightly 的结论越来越不可用。

**当前覆盖口径**：会议 / 邮件 / 云效 / 大事儿已经自动汇入；
本机文件与聊天这两类，只靠上面四个入口——这正好是最容易漏、也最有信息量的一半。
